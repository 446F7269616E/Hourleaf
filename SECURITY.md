# Security Policy

## Supported versions

Security fixes target the latest public release. Release notes will identify any supported older versions; otherwise, only the latest release is supported.

## Reporting a vulnerability

Do not open public issues for unpatched vulnerabilities or include real user data, browser profiles, store credentials, or publicly exploitable proofs of concept.

Use **Security → Report a vulnerability** in the GitHub repository. If private vulnerability reporting is unavailable, open an issue requesting a private contact channel without disclosing technical details.

Include:

- Affected version, browser, and operating system.
- Vulnerability type, impact, and prerequisites.
- Minimal reproduction steps or a proof of concept using synthetic data.
- Suggested mitigation, if available.

The maintainer aims to acknowledge reports and provide an initial assessment within seven days. Fix timing depends on impact, platform review, and release requirements. Coordinate disclosure until a patch is widely available. Reporters are credited in security advisories with their consent.

## Scope

In scope: permission abuse, cross-site or extension-page code execution, forged privileged messages, data exfiltration, unauthorized usage-data access, supply-chain/update integrity, and bypasses of critical focus rules.

Display-only module compatibility issues without security or privacy impact, attacks requiring complete control of the local device/profile, social engineering, and automated findings without verified impact are normally handled as ordinary bug reports.

## Research safety

Use your own test accounts and synthetic data. Do not access, modify, or retain others' data, disrupt services, or bypass store security controls. Stop and report privately if you encounter credentials or user data.
